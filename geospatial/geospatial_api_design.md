# Geospatial API design

For the FDRI project there is a requirement to be able to easily visualise geospatial data, predominantly stored in raster and vector formats.

In order to be able to display raster data on a UI it must be split into tiles, which are then served via an API. There are many ways to do this, but the options can be split into two categories - serving pre-generated raster tiles, or dynamically creating the raster tiles from a single raster file.

As one of the ideas behind the design of the geospatial API is to create something that will not only accomodate all FDRI geospatial requirements, but is also able to be easily re-used for any other projects that may need to display and interact with geospatial data.

With this in mind, dynamically generating tiles from raster data stored in S3 appeared to be the most
flexible solution. Not only would it mean a single raster is stored in S3 instead of hundreds of thousands of tiny image tiles, but also provides the ability to download the raw raster data directly from S3 if needed, as TiTiler (the main library supporting dynamic tile generation) has the ability to colourise a raster during the tile generation process. However dynamic colourisation does slow down the API response, so it may be better to store a pre-colourised version of the raster data.

## Current implementation structure

The geospatial api provides an interface between the spatial explorer UI and a variety of sources. Information on where each layer is sourced from is provided using the postgis database, details of which can be found in the [database design](#database-design) section.

### Data requirements

More details of data requirements can be found in the separate file: [geospatial_data_types](geospatial_data_types.md)

#### Raster

In order for a raster to be easily displayed using TiTiler, it must be formatted to have the following attributes

- Reprojected into EPSG 3857 (world mercator projected equivalent to WGS84)
- Colourisation applied
- Converted to a COG formatted raster
- Any corresponding legend data generated and stored alongside the raster

#### Vector

At present, vector layers are rendered directly from geojson served by the API. This can either be sourced from a geojson file stored on S3, or from the metadata api. Complex vector data (e.g. 10MB+ geojson files) is not able to be served performantly using this method and it is recommended to rasterize the layer until a suitable alternative is developed. The requirements for formatting the vector data are:

- Reprojected into EPSG 4326 (WGS84)
- Converted to geojson format
- Any complex geometries are simplified (but not to the point where accuracy of the geometry is reduced when viewed on the UI)

### Linking data on S3 to the UI via an API

A basic FastAPI instance is used to find the data stored in S3, undertake any processing to make the data easily renderable, before passing it out to the UI.

<img src="./images/basic-geospatial-api.png">

TiTiler is used to dynamically create raster tiles (generally png images of the raster at various zoom levels) as they are requested by the UI. This avoids hundreds of thousands of tiny png files needing to be stored either on S3 or in a database somewhere.

#### Endpoints

There are three main endpoints to the data (see https://dri-geospatial-api.staging.eds.ceh.ac.uk/api/docs for the documentation):

- **/available_data** Lists the layer information from the postgis database. The intention is that this endpoint returns all required metadata and configuration parameters required by the UI to render the layer, but will not serve the layer data itself (i.e. no geojson data or similar will be returned).
- **/maps/tiles/** This endpoint (and it's various variations) requests dynamic raster tiles generated by TiTiler and serves them to the UI. The urls are often in the format of /maps/tiles/{tileMatrixSetId}/{z}/{x}/{y}.png?url={s3Url}. For example http://localhost:8000/api/maps/tiles/WebMercatorQuad/16/32261/21043.png?url=S3://ukceh-fdri-staging-geospatial/raster/test_raster_3857_cog_rendered.tif.
- **/vector** Reads data from the requested vector file from S3 or decodes site information from the Metadata API and returns it as a geojson object, ready to be rendered directly by the UI.

In addition there are a number of extra endpoints used for serving supporting data to the UI (such as location boundaries), or for managing the postgis database. See [layer management](layer_management.md) for details.

## Database design

### Main table

A registry of layers, containing a spatial index is required. The structure of the main table is as follows:

| Column Name             | Required? | Description / Notes                                                                                                                                                                  |
| ----------------------- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| ID                      | Required  | Primary key created by the database                                                                                                                                                  |
| Name                    | Required  | Used for displaying the name in the UI                                                                                                                                               |
| Description             | Optional  | A basic description to associate with the layer, where appropriate.                                                                                                                  |
| Project                 | Required  | FDRI/ NC-UK etc – Links to project table                                                                                                                                             |
| Date                    | Optional  | The single date to associate with the layer. If not provided then it is assumed either a start date will be present, or that the layer has no date information available.            |
| Start Date              | Optional  | The start date for a dataset.                                                                                                                                                        |
| End Date                | Optional  | The end date for a dataset. This is an optional field as many layers may have ongoing data collection.                                                                               |
| Source type             | Required  | Links to the SourceType table to provide information about where the data is coming from (e.g. S3, metadata api etc)                                                                 | 
| Raw Source id           | Optional  | The S3 key, catalogue identifier etc to point the API to the raw data (if available). This should be the singleband EPSG 3857 COG tif or any vector (geojson) data.                  |
| Colour Source id        | Optional  | The S3 key, catalogue identifier etc to point the API to the colourised data (if available). It's expected this will be a cog formatted colourised raster, or a WMS source.          |
| Layer id                | Optional  | The name of the WMS layer to fetch. This may also be used in the future for identifying which vector layer to extract from a geopackage or similar type uses.                        |
| Data format             | Required  | Raster / vector etc. Links to the DataFormat database table                                                                                                                          |
| Data category           | Required  | DOM / DEM etc. Links to the DataCategory database                                                                                                                                    |                                                                                                                                                              |
| Legend (JSON)           | Optional  | A categorical or range based legend which is expected to correspond to the source layer information.                                                                                 |
| Boundary                | Optional  | Simplified boundary in WGS84 to allow for location queries. If not provided then the location boundary is used instead.                                                              |
| Bounding box (bbox)     | Required  | Bounding box (in WGS84) of the layer stored as a geometry (not a list of 4 floats)                                                                                                   |
| Processing level        | Required  | Links to the ProcessingLevel database table. Aims to identify whether data is raw or processed.                                                                                      |
| Location                | Required  | Links to the Location database table. Defines the locatiion associated with the layer (e.g. Chess) which then links to the type of location (e.g. Catchment).                        |
| Field metadata          | Optional  | Used for decoding site information from the Metadata API, in addition to informing the UI which fields should be displayed from geojson feature properties                           |
| Filter metadata         | Optional  | Similar to the `field_metadata` field, but used for filtering individual geometries from vector data. It is anticipated this will be used in conjuction with `filter_metadata` but                           |
| Field metadata          | Optional  | Used for decoding site information from the Metadata API, in addition to informing the UI which fields should be displayed from geojson feature properties                           |

### Project table - project metadata and data categorisation

Stores the project ids and unique project specific parameters. For example FDRI may want to categorise data based on
the region, data type and date range, whereas a different project may want to categorise based on data type and
resolution. The project metadata can then be used to derive the S3 structure.

The project table could have the following fields (likely to be expanded):

| Column Name | Required? | Description / Notes                                      |
| ----------- | --------- | -------------------------------------------------------- |
| ID          | Required  | Primary key created by the database                      |
| Object key  | Required  | Used as a unique ID for easily finding the correct item. |                                                                                                                                                                                                   
| Name        | Required  | Used for displaying the name in the UI                   |

### Location

This links to the location field in the main Layer table, and stores details about the location associated with the layer.
Its use case is to create instances of different locations, each with a unique name that can be easily associated with
multiple layers without risking duplication due to typos (e.g. one layer referred to as "chess", another as "Chess", another as "Chess Catchment" etc)
This table stores the name to use for the area associated with the layer, and links to the type of area it corresponds to.

| Column Name | Required? | Description / Notes                                      |
| ----------- | --------- | -------------------------------------------------------- |
| ID          | Required  | Primary key created by the database                      |
| Object key  | Required  | Used as a unique ID for easily finding the correct item. |                                                                                                                                                                                                   |

| Area type   | Required  | Links to the AreaType table                              |

## Still in progress 

The method for serving vector data too large to be sent via API still needs to be determined. Some form of vector tiles
seems promising as it would allow feature selection within the UI. Current attempts to implement this have yet to be 
successful.
